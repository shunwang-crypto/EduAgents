# 对话模块分享讲稿规划

> 配合《对话模块设计分享.docx》使用。按师兄要求编排：**设计思路讲"规划做了哪些功能（有层次）"，示意图讲"内部组件关联 + 跨模块交互"**。
> 默认按 10 分钟规划，个性化部分约占一半；文末附 5 分钟压缩版。

## 讲述总原则

1. **先讲我做了什么，再讲它在系统里的位置**——开场 30 秒内让听众知道你的四块能力，不要先铺系统背景。
2. 每一层功能都落到"做了什么、为什么这样分"，层次感靠 L1→L4 的递进讲出来。
3. 讲图时**顺着连线讲**：先内部组件怎么协作，再跨出去讲和伙伴模块怎么配合。

---

## 开场：我是谁、我做了什么（约 1 分钟）

**讲的内容**（对应文档第 1 章，按"定位 → 背景 → 功能总览"三步走）：

> "我负责对话模块，负责系统里的对话问答能力：**一个对话服务统一承载全部对话场景，并在对话过程中完成画像的记忆采集**。它在系统里有两个身份——用户侧的统一交互入口，和学习者画像的主要采集入口。"

**系统背景一句带过**（不展开，细节在图 1 讲）：

> "知行课径围绕'诊断—学习—检验—纠错'闭环，画像、测评、讲解、纠错是伙伴基于星辰工作流做的；画像由画像工作流和后端事件累计维护，我负责从对话里采集。"

**功能总览指着表 1 讲**（这是"做了哪些功能"的第一次完整亮相）：

> "我的功能分四层，从上到下是场景、会话、上下文、记忆——也对应实现顺序：先保证能聊，再保证聊得好，最后让聊天反哺系统。下面逐层展开。"

## 第一部分：设计思路——功能怎么分层规划的（约 2 分钟）

**先讲分层逻辑**（对应第 2 章开头）：

> "功能分四层，每层只依赖下一层；分层依据是离用户的距离，也对应实现顺序：先保证能聊（场景与会话），再保证聊得好（上下文个性化），最后让聊天反哺系统（记忆）。"

**展示表 1**，然后逐层讲，每层固定节奏"职责一句 → 功能点 → 关键机制"：

- **L1 场景层**（表 2）：职责是"定义三个入口和各入口携带的上下文"，三个入口一张表带过，重点讲设计取舍——"三个场景用参数区分，而不是拆三个服务，因为场景差异只是上下文不同，不是业务不同"。
- **L2 会话层**：职责是"对话的组织与持久化"，四个功能点（多会话 / 自动标题 / 历史恢复 / 权限安全）各念一句，权限点强调"不区分'不存在'和'无权限'"。
- **L3 上下文层**：职责是"决定回答的个性化程度"，核心原则一句——"**按需挑选，而不是全量加载**"，画像只挑相关的、转成自然语言再给模型；偏好分正负向；资料检索用"步骤标题 + 问题"做查询。
- **L4 记忆层**：先用三个行为例子开场——"'我会 Python、喜欢看代码示例'之后的对话就用上了；'以后回答简洁一点'风格就变；'忘记我做过 FastAPI'就真的删掉"；再说明双路径的职责边界：新增和更新走受约束的语义抽取，模型失败才用规则回退；删除始终走确定性规则。

## 第二部分：个性化闭环——重点讲清楚（约 4 分钟，核心）

先给结论：

> "这里的个性化不是给每个学生重新训练一个模型，而是在每次回答和生成计划之前，从持久化的学习者画像库中挑选当前真正相关的信息，再转成人话注入模型。与此同时，对话又会把稳定的新信息写回画像，所以它是一个读写闭环。"

按五步顺序讲，听众最容易记住：

1. **采集**：用户在自然对话里说出技能、背景、经历和长期偏好；纯提问没有自述信号，不调用抽取模型。
2. **结构化存储**：信息不是一段随意的总结，而是分为学习者背景事实、学习偏好、长期语义记忆和课程学习状态；SQLite 画像库是唯一真值。
3. **按场景筛选**：普通对话取全局画像；课程对话再取本课程目标、计划、背景和资料；步骤提问继续增加知识点、前置和难度。其他课程背景严格过滤。
4. **注入生成**：内部键先转成“已掌握 Python”“优先代码示例”这样的自然语言，再与最近历史和当前问题一起组成提示词。
5. **反馈复用**：聊天中记住的 Python 背景，既让下一轮回答优先用代码，也会让计划生成压缩 Python 入门，从而把“对话中说的”变成“学习路径里用的”。

现场举一个贯穿例子：

> "用户说'我会 Python，更喜欢代码示例，不太喜欢纯理论'。系统先抽取成技能事实和两个正负向偏好，经过白名单、长度和敏感信息校验后写入画像。下一轮问依赖注入时，上下文里已经是'已掌握 Python、优先代码示例、避免纯理论优先'，所以模型可以直接用 FastAPI 代码讲，而不从抽象定义开始。"

然后补充两点安全边界：

- 新增和更新只允许 `set_fact / set_preference / add_memory`，模型不能覆盖整份画像，也不能删除。
- “忘记 Java”由规则精确匹配已有画像，不会误删 JavaScript；删除在构建本轮上下文前完成，会立即生效，新写入记忆则从下一轮生效。

## 第三部分：示意图——组件关联与跨模块交互（约 2 分钟）

**图 1（约 45 秒）——总览，先内后外**：

> "看中间这块，对话模块内部五个组件：**会话管理**接到消息后驱动**历史管理**和**记忆引擎**；**上下文构建器**把课程、计划、画像、资料挑出来，和**历史**一起汇入**回复生成**。"
> "再看右边和伙伴模块的交互：我是画像的**读端也是写端**——读画像工作流维护的学习者画像，把聊天提取的记忆回写；目标规划、学习讲解、纠错讲解给我步骤和纠错上下文，支撑'就此提问'；知识库提供检索；模型能力统一走星辰平台。"

**图 2（约 45 秒）——一次请求的完整流程**：顺着时序走一遍（校验 → 建会话 → 规则删除 → 读历史 → 存消息 → 构建上下文 → **并行**生成回复与提取记忆 → 校验入库 → 保存返回），然后强调两个顺序设计：

> "第一，**先读历史、后存当前消息**，保证当前消息在提示词里只出现一次；第二，**校验全部前置**，任何校验失败都不会留下脏数据。"

**图 3 和图 4（约 30 秒）**：图 3 强调“删除确定性、写入受约束”的职责边界；图 4 强调有课程时使用完整课程上下文，无课程时沿用全局画像，个性化构建异常时仍保留课程名、目标和计划摘要作为最低保障。

## 第四部分：决策与收尾（约 1 分钟）

**表 4 挑三个讲**（不要逐行念）：

1. "一个对话服务承载三场景"——避免业务爆炸；
2. "删除只走规则通道"——误删代价远大于漏删，"忘记"是用户显式指令，必须确定性执行；
3. "回复与记忆提取并行"——记忆提取不增加回复延迟，新记忆下一轮生效。

**收尾**（对应第 4 章最后一段）：

> "总结：对话模块 = 三场景统一的会话服务 + 按需挑选的个性化上下文 + 双通道安全记忆引擎。对用户，越用越懂你；对系统，它是画像的主采集入口——**让'对话中说的'变成'学习路径里用的'**。"

## 预设提问与回答

| 可能被问 | 回答要点 |
|---|---|
| 为什么不让大模型直接改画像？ | 模型输出不可信；结构化写入可校验、可审计、可回滚，删除只走确定性规则 |
| 记忆会不会越记越多、记错？ | 无自述信号不抽取；提示词有克制原则（临时指令不入库）+ 四道防线过滤 + 已有画像去重 + “忘记”可删 |
| 新记忆什么时候生效？ | 新写入记忆通常下一轮生效；确定性删除在本轮上下文构建前执行，因此立即生效 |
| 个性化是不是微调模型？ | 不是。核心是持久化学习者画像库 + 运行时上下文选择；模型本身可以替换，画像数据和筛选规则仍由系统控制 |
| 和伙伴的画像模块怎么分工？ | 画像工作流 + 事件累计维护画像真值，我负责从对话里采集并结构化回写，读端写端都走统一入口 |
